# 2026-11-18: security.txt and robots.txt exposure (roadmap step 9)

## Plan
1. Generalise the fetch loop in `scanUrl()` so a second entry point,
   `fetchText()`, can read small text files under the *same* SSRF guard,
   timeouts and redirect rules, instead of writing a second HTTP client.
2. One pure module per file: a parser plus a `checkX(observation)` grader.
3. A probe that fetches `/.well-known/security.txt` (falling back to the
   legacy `/security.txt`) and `/robots.txt` from the target's origin, and
   scores them as their own `WellKnownReport`, like the TLS, content and DNS
   sections.
4. Unit tests on fixtures; integration tests against local http/https servers
   on 127.0.0.1.

## Built
- `scan/scan-url.ts`
  - The redirect loop moved into an internal `followChain()`, parameterised by a
    `BodyPolicy` (Accept header, byte limit, which responses to read).
    `scanUrl()` is now a thin wrapper over it; behaviour unchanged (its 70
    existing tests pass untouched).
  - New `fetchText(url, { maxBytes, accept, ...ScanOptions })`: reads only 2xx
    bodies, bounded (default 64 KiB), and *returns* non-2xx statuses rather
    than throwing, so callers can tell "missing" from "unreachable". The
    `accept` value is validated against CR/LF/NUL (header injection).
- `wellknown/observation.ts`: `WellKnownObservation`, a tagged union
  `found | missing | error` that the graders consume.
- `wellknown/security-txt.ts` (10 pts), RFC 9116:
  - `parseSecurityTxt()`: case-insensitive `Field: value` lines, comments,
    BOM, OpenPGP cleartext-signed files (armour stripped, dash-escapes undone;
    the signature is detected, not verified). Never throws; malformed lines
    become problems.
  - `parseExpires()`: strict RFC 3339 date-time with an offset; rejects
    date-only values and calendar overflow (Feb 30), without a backtracking regex.
  - `checkSecurityTxt(obs, now)`:
    - pass (10): HTTPS, `text/plain`, ≥1 valid Contact, future Expires;
    - warn (7): only at the legacy path, wrong/missing Content-Type, Expires more
      than a year out, cross-host redirect, signed without Canonical;
    - fail (3): no Contact or Expires, expired, duplicate Expires/Preferred-Languages,
      non-URI or `http://` URIs, Canonical not matching where it was served,
      served over HTTP, larger than 32 KiB;
    - warn (0): not published; info (unscored): network error.
- `wellknown/robots-txt.ts` (10 pts):
  - `parseRobotsTxt()`: RFC 9309 groups (consecutive `User-agent` lines share a
    group), Allow/Disallow, Sitemap, comments; keeps at most 5000 rules.
  - `classifyPath()`: whole-segment matching against an ordered pattern table:
    **high** = source control (`.git`, `.svn`…), secrets/config (`.env*`,
    `wp-config`, `*.pem`), backups/dumps (`backup/`, `*.sql`, `*.bak`);
    **medium** = admin panels, installers, logs, staging/dev/tmp, "internal/private";
    **low** = framework defaults (`/wp-admin/`), reported but not penalised.
  - `checkRobotsTxt()`: nothing sensitive or no file → pass (10); medium → warn 7;
    any high → warn 3, with up to 8 example paths.
- `wellknown/probe.ts`: `fetchWellKnown()` classifies a fetch (2xx text →
  found; non-2xx, HTML catch-all or empty → missing; network failure → error),
  and `analyzeWellKnown(target, options)` runs both files in parallel and
  returns `WellKnownReport` (findings, score/grade, observations, parsed
  security.txt fields, sensitive robots paths).
- Tests: 732 Vitest tests (was 625): 107 new in `wellknown-security-txt`,
  `wellknown-robots-txt` (pure, fixtures) and `wellknown-probe` (real sockets:
  one https + one http server on 127.0.0.1, Host-header routing for
  `good/legacy/spa/redir/slow/big/echo.test`, a test CA minted per run).
  pytest unchanged at 119. ESLint (security plugin, zero warnings), Prettier,
  `tsc`, bandit and the secrets grep are clean (the grep's `-----BEGIN` hits
  are PGP armour markers in the parser and fixtures, not keys). `pnpm audit`:
  the known moderate `minimatch` via eslint (dev-only); last week's `picomatch`
  advisory no longer appears.

## Design decisions worth explaining
- **Why these two files.** They're opposite sides of disclosure.
  *security.txt* is disclosure you *want*: it tells a researcher who found a
  bug where to report it, so reports reach the security team instead of a
  support inbox or Twitter. Its `Expires` field exists because stale contacts
  are worse than none (reports go to a mailbox nobody reads).
  *robots.txt* is disclosure you usually *don't* want: it's a public file and
  only a polite request to crawlers, so `Disallow: /backup-2023/` hides the
  path from Google and hands it to every attacker who reads the file. Recon
  tooling reads robots.txt first for exactly that reason.
- **One HTTP client, two entry points.** Rather than calling undici directly
  for the new files, I extracted the redirect loop from `scanUrl()` into
  `followChain()` and built `fetchText()` on it. Every request the scanner
  makes still goes through one code path that re-validates each redirect hop
  against the SSRF policy. A second, slightly different client is exactly how
  SSRF bugs creep in: `/robots.txt` that 301s to `169.254.169.254` is refused
  the same way a page redirect is (there's an integration test for it).
- **The scanner reports, it doesn't probe.** robots.txt findings say "this
  path is *advertised*", not "this path is exposed": the scanner never
  requests the listed paths. Fetching `/.git/config` because robots.txt
  mentions it would move the tool from auditing configuration to actively
  probing someone's server, which needs a different level of authorisation
  (that's what the ownership verification in step 17 is for). The test
  asserts that only the three well-known paths were requested.
- **"Missing" vs "unreachable" vs "fake 200".** A 404 is an answer (no file).
  A timeout says nothing about the site, so it becomes an unscored `info`
  finding (same rule as the DNS checks: flaky networks shouldn't lower a
  grade). And a 200 with `text/html` is treated as missing: SPAs and many
  CMSs return their HTML shell for every path, which would otherwise "pass"
  as a security.txt full of malformed lines.
- **Whole-segment matching, ordered by severity.** `/administration-guide`
  isn't an admin panel and `/blog/backups-explained` isn't a backup, so paths
  are split into segments and compared exactly (or by stem/extension),
  never by substring. A path matches its *most* severe category
  (`/admin/backup.sql` is a backup). Archive extensions (`.zip`, `.gz`) are
  deliberately left out: sites commonly disallow crawling their downloads.
- **Framework defaults cost nothing.** Every WordPress site lists
  `/wp-admin/`; it reveals nothing an attacker doesn't already know from the
  page source, so penalising it would just make the grade noisy. It's still
  shown in the detail.
- **Bounded input everywhere.** Both files are attacker-controlled: reads
  are capped (32 KiB for security.txt, 512 KiB for robots.txt, the minimum
  RFC 9309 says crawlers must handle), robots rules are capped at 5000, and
  parsing uses `indexOf`/`split` and short anchored regexes. The first
  `parseExpires` regex was flagged by the ESLint security plugin as
  potentially catastrophic, so it was replaced with fixed-position checks.
- **Injectable clock.** `checkSecurityTxt(obs, now)` and
  `analyzeWellKnown(..., { now })` take the current time, so "expired" and
  "more than a year away" are tested deterministically instead of with
  fixtures that silently start failing next year.
- **Signed but not verified.** OpenPGP-signed files are unwrapped so their
  fields are graded, and the report says "signature not verified": verifying
  needs the owner's public key, which the scanner has no trustworthy way to get.

## How to try it
```bash
corepack enable && pnpm install
pnpm check                                                       # lint + format + tsc + 732 tests
pnpm --filter @header-auditor/core exec vitest run wellknown     # just today's tests
cd cli-python && pytest -q                                       # 119 tests
```

```ts
import { checkRobotsTxt, checkSecurityTxt, analyzeWellKnown } from "@header-auditor/core";

const obs = (path: string, text: string) => ({
  kind: "found" as const,
  url: `https://example.test${path}`,
  path,
  finalUrl: `https://example.test${path}`,
  statusCode: 200,
  mediaType: "text/plain",
  text,
  truncated: false,
  redirects: [],
});

// Pure grading, no network.
checkRobotsTxt(obs("/robots.txt", "User-agent: *\nDisallow: /.git/\nDisallow: /admin/")).score; // 3
checkSecurityTxt(
  obs("/.well-known/security.txt", "Contact: mailto:sec@example.test\nExpires: 2027-06-30T00:00:00Z"),
).status; // "pass"

// Against a site you own (or a local server with allowPrivate: true):
const report = await analyzeWellKnown("https://your-site.example/");
console.log(report.grade, report.findings.map((f) => `${f.check}: ${f.status}`));
```
