# 2026-11-24: Scan queue and worker (roadmap step 15)

## Plan

1. `packages/queue`: one shared contract for the producer (API) and the
   consumer (worker): queue name, job payload validator, job options, and
   `REDIS_URL` parsing.
2. API: a `ScanStore` (memory + Prisma), a `ScanQueue` port with a BullMQ
   adapter, and `POST /sites/:id/scans` + `GET /sites/:id/scans/:scanId`.
3. Database: a migration with a partial unique index so a site can only have
   one queued or running scan.
4. `apps/worker`: config, the engine run (all core checks), a claim/lease
   store, the job processor, the BullMQ binding and a process entry point.
5. Make the workspace packages runnable and testable without a build step
   (the "runnable `@header-auditor/db`" gap from yesterday).
6. Tests at every layer, ending with the whole pipeline on a real Redis and
   PGlite against a mock site on 127.0.0.1.

## Built

- **`packages/queue`** (new, no runtime dependencies):
  - `SCAN_QUEUE_NAME`, `SCAN_JOB_NAME`, `DEFAULT_QUEUE_PREFIX`.
  - `parseScanJobData()` accepts exactly `{ scanId: <lower-case uuid> }`.
    Extra keys, other types or a non-UUID are rejected.
  - `scanJobOptions(scanId)`: `jobId = scanId`, 3 attempts, exponential
    backoff from 5 s, finished jobs trimmed from Redis after a day (failed
    ones after a week).
  - `parseRedisUrl()` / `redisConnectionOptions(url, role)` /
    `redactRedisUrl()`. `producer` (API) fails fast, `consumer` (worker) uses
    `maxRetriesPerRequest: null` as BullMQ requires. Errors never echo the
    URL, because it holds the password.
- **API** (`apps/api/src/scans/`), enabled with `buildApp({ ..., scans: {
  store, queue } })`:
  - `POST /sites/:id/scans` → `202 Accepted` + `Location:
    /sites/:id/scans/:scanId`. `404 SITE_NOT_FOUND` for someone else's site
    (same body as a missing one). `409 SCAN_IN_PROGRESS` with the running
    scan's `Location`. `429 SCAN_LIMIT_REACHED` at the per-user limit.
    `503 QUEUE_UNAVAILABLE` if Redis refuses the job, and then the scan row
    is marked FAILED so the site isn't blocked. A request body is rejected
    (400), since there are no options yet.
  - `GET /sites/:id/scans/:scanId` → status, and when finished the grade,
    score, findings (in engine order) and the full JSON report. Ownership is
    a join on `sites.owner_id`. Another user's scan is a 404, even when
    requested through their own site's URL.
  - `createPrismaScanStore()`: in one transaction it locks the owner's
    `users` row, checks the site belongs to the owner, closes out stale
    scans, checks per-site and per-user limits, and inserts. The URL is
    copied from the site row.
  - Config: `SCANS_MAX_ACTIVE_PER_USER` (5), `SCANS_ACTIVE_WINDOW_MINUTES`
    (15). Documented in `.env.example`.
- **Migration `20261124000000_scan_queue`**: partial unique index
  `scans_one_active_per_site_key ON scans(site_id) WHERE status IN
  ('QUEUED','RUNNING')`, and a CHECK that a RUNNING scan has `started_at`.
- **`apps/worker`** (new):
  - `runEngine()`: phase 1 `scanUrl` (headers, redirects, mixed content, SRI
    with the site's `firstPartyHosts`) is required. Phase 2 runs TLS (https
    only), DNS (hostnames only) and security.txt/robots.txt in parallel. Each
    phase 2 section is `ok`, `skipped` or `error`.
  - Target failures become a `TargetError` with a fixed message per core
    error code (`FAILURE_MESSAGES`), never the raw error text.
  - `createScanProcessor()`: validate payload → claim → run → save. A target
    failure is saved as a FAILED result (no retry). An infrastructure failure
    releases the claim and rethrows so BullMQ retries.
  - `createPrismaWorkerStore()`: `claimScan`, `completeScan` (status +
    findings in one transaction), `failScan`, `releaseScan`, `abandonScan`.
    All writes are fenced on the lease.
  - `startScanWorker()`: BullMQ `Worker` with concurrency and
    `lockDuration`. When a job's last attempt fails, its scan is marked FAILED.
  - `main.ts`: zod config (`DATABASE_URL`, `REDIS_URL`, `QUEUE_PREFIX`,
    `WORKER_CONCURRENCY`, `WORKER_SCAN_TIMEOUT_MS`,
    `WORKER_STALE_AFTER_SECONDS`, `WORKER_SHUTDOWN_TIMEOUT_MS`,
    `WORKER_ALLOW_PRIVATE_TARGETS`, refused in production), pino with
    redaction, and graceful shutdown on SIGTERM that waits for running scans.
- **core**: `scanUrl()` takes `firstPartyHosts` and passes them to the SRI
  check (+1 test).
- **Workspace plumbing**: packages export their TypeScript source under a
  custom `@header-auditor/source` condition and their built `dist/` for
  everyone else. `tsconfig.base.json` sets `customConditions`, build configs
  clear it, and `vitest.shared.ts` adds it for tests. `packages/db` now has a
  `build`, so the worker and API can run from `dist/` in production. Root

- **CI**: a `redis:7.4-alpine` service on 127.0.0.1 (`TEST_REDIS_URL`) and a
  `pnpm build` step.

## Design decisions worth explaining

- **Why a queue at all.** A scan makes a dozen outbound connections and can
  take 30+ seconds. Holding an HTTP request open that long ties up the API
  and times out behind proxies. And the API process (which holds sessions
  and the database) shouldn't be the one connecting to arbitrary hosts. The
  API records intent (a QUEUED row) and returns `202 Accepted` with a
  `Location` to poll. A separate worker, which can be sandboxed and scaled
  on its own, does the network work.
- **The job carries only the scan id.** Anyone who can write to Redis can
  create jobs. If the payload carried the URL, a Redis compromise would mean
  "make the worker fetch anything" (SSRF by queue injection). With an id
  only, the worker reads the URL from Postgres, which went through the API's
  validation and ownership checks. A forged job can at most re-run an
  existing scan. The payload validator rejects extra keys, and a test sends
  `{ scanId, url: "http://169.254.169.254/" }` to prove it.
- **The SSRF guard lives in the worker.** The API refuses IP literals and
  `localhost` when a site is added. But `evil.example.com` can resolve to
  `10.0.0.1`, or switch to it later (DNS rebinding). The worker runs every
  connection through core's connect-time address check. A test points
  `shop.test` at 127.0.0.1 and gets `BLOCKED_ADDRESS` before the mock site
  sees a single request.
- **At-least-once delivery, made safe.** BullMQ guarantees a job runs *at
  least* once. If a worker stalls, its lock expires and the job is given to
  another worker, even if the first one is still alive. So the worker must
  be idempotent, and the database does that:
  1. *Claim* is a conditional `UPDATE ... SET status='RUNNING',
     started_at=now WHERE id=$1 AND status='QUEUED'`. Two workers can't both
     win it.
  2. A RUNNING scan older than `WORKER_STALE_AFTER_SECONDS` (its worker
     died) can be re-claimed.
  3. `started_at` is a **fencing token**: results are only written `WHERE
     status='RUNNING' AND started_at=<my lease>`. If worker A stalls, B
     re-claims and finishes, then A wakes up, A's write matches zero rows.
     The test runs that exact interleaving and checks B's result survives.
  4. `jobId = scanId`, so enqueueing the same scan twice is a no-op in
     BullMQ.
  Config enforces `stale window > 2 × scan timeout`, so a healthy scan is
  never treated as dead.
- **Result vs. retry.** "The site timed out" is a valid answer about the
  site, saved as FAILED and not retried (retrying would just hit the target
  again). "Postgres is down" is our problem: the worker hands the claim back
  (RUNNING → QUEUED) and rethrows, so BullMQ retries with backoff. Without
  the release, the retry would find the scan RUNNING and skip it. After the
  last attempt, the `failed` handler marks the scan FAILED so nobody sees
  "running" forever.
- **One active scan per site, enforced by the database.** The API checks
  this inside a transaction, but checks in application code can lose races.
  (PGlite runs every connection in one session, so the row lock couldn't
  serialize the test's concurrent requests, which is what exposed this.) The
  partial unique index `ON scans(site_id) WHERE status IN
  ('QUEUED','RUNNING')` makes a second active scan impossible at any
  isolation level and with any number of API instances. A lost race shows up
  as a unique violation, and the store retries once and answers "in
  progress". A test forces that race. Stale scans are marked FAILED inside
  the same transaction, so a dead worker can't block a site forever.
- **Two limits, two purposes.** One active scan per site stops hammering one
  target. `SCANS_MAX_ACTIVE_PER_USER` stops one account from filling the
  shared queue (50 sites × 1 scan each would still be 50 jobs). The first is
  a 409 (a conflict with an existing resource, with its `Location`), the
  second a 429 (rate limiting).
- **Enqueue failure doesn't leave a phantom.** Insert the row, then enqueue:
  if Redis is down, the row would sit QUEUED forever and block the site. The
  route marks it FAILED (only if it is still QUEUED) and returns 503 with no
  Redis details. The fully robust version is a *transactional outbox*: write
  the job into Postgres in the same transaction, and have a relay push it to
  Redis. It's worth it once scheduled scans (step 16) enqueue in bulk.
- **Fixed failure messages.** Errors from the network layer can contain
  resolver output or internal addresses. The worker stores one fixed sentence
  per error code (`FAILURE_MESSAGES`) and logs the details. An engine bug
  stores "internal error" and logs the stack trace.
- **NUL bytes.** Postgres rejects `\u0000` in text and jsonb. A hostile page
  could put one in a body-derived string to make its own scan unsaveable.
  The report is serialized with a replacer that strips NULs. Findings
  already go through `stripNul` in `packages/db`.
- **Why `@header-auditor/source` instead of building first.** Tests and
  type checks resolve workspace packages to their `src/` through a custom
  export condition, so `pnpm test` always runs against the code on disk with
  no stale `dist/`. Production (`node dist/main.js`) uses the default
  condition, meaning compiled JavaScript. Build configs clear the condition,
  so each package compiles only its own `src`. Vite replaces its condition
  list rather than prepending to it, so the shared config re-adds
  Vite's defaults. Leaving out `"module"` broke how `pg` loads `pg-pool`.
- **Shared contract package.** Queue name, payload and options live in one
  place both apps import. Rename the queue and both sides change together,
  instead of jobs piling up in a queue nobody listens to.
- **BullMQ 5.81.5, not 6.x.** 6.x is new (July) with a reworked backend
  model, and its patch releases are still landing daily. 5.81.5 is a
  maintained, two-month-old release of the API this code targets. The
  `msgpackr-extract` native install script stays unapproved: it's an
  optional speed-up and msgpackr falls back to JavaScript.
- **Tests use real infrastructure where it matters.** The store contract
  runs on both the memory store and PGlite, because only real SQL can show a
  wrong `WHERE` or a missing index. The pipeline test uses a real Redis
  (spawned on a random loopback port with a random password, or CI's service
  container), BullMQ, the API, the worker and the engine against a mock site.
  If Redis isn't available, the suite fails rather than skipping. A skipped
  queue test would let a broken queue pass.

## How to try it

```bash
corepack enable && pnpm install
pnpm test                                         # all packages (worker needs redis-server or TEST_REDIS_URL)
pnpm --filter @header-auditor/worker test         # 49 tests, including the real-Redis pipeline
pnpm build                                        # core, db, queue, api, worker → dist/
```

Running the worker locally:

```bash
cp .env.example .env            # set real local passwords
docker compose up -d            # Postgres + Redis on 127.0.0.1
pnpm --filter @header-auditor/db migrate:deploy
pnpm build
set -a; . ./.env; set +a
node apps/worker/dist/main.js   # logs "worker ready"; Ctrl-C waits for running scans
```

In code (the API still takes injected stores, see Next):

```ts
import { Queue } from "bullmq";
import { SCAN_QUEUE_NAME, redisConnectionOptions } from "@header-auditor/queue";
import { buildApp, createBullScanQueue, createPrismaScanStore /* ... */ } from "@header-auditor/api";

const queue = new Queue(SCAN_QUEUE_NAME, {
  connection: redisConnectionOptions(process.env.REDIS_URL, "producer"),
});
const app = await buildApp({
  config,
  auth,
  sites,
  scans: { store: createPrismaScanStore(prisma), queue: createBullScanQueue(queue) },
});
```

```bash
curl -s -b jar -X POST -H origin:http://localhost:3000 -H x-csrf-token:<csrfToken> \
  http://127.0.0.1:3001/sites/<siteId>/scans            # 202, Location: /sites/<siteId>/scans/<scanId>
curl -s -b jar http://127.0.0.1:3001/sites/<siteId>/scans/<scanId>   # queued → running → succeeded
```

## Next

scan history endpoint.

Known gaps:

- **API startup wiring.** `start()` still takes injected stores. The worker
  now proves the pattern (config → Prisma client → BullMQ), and `@header-auditor/db`
  builds, so step 16 should add `DATABASE_URL`/`REDIS_URL` to the API config
  and wire the Prisma stores, the BullMQ queue and `/health/ready` checks for
  Postgres and Redis. Scheduling needs that anyway.
- A transactional outbox for enqueueing (see above). It matters most for
  bulk scheduled enqueues.
- A queued scan waiting longer than `SCANS_ACTIVE_WINDOW_MINUTES` (a big
  backlog) is closed out by the next POST for that site. Fine at this scale.
  With real backlogs, track `queued_at` vs. `started_at` and alert on queue
  depth.
- The worker container should run with outbound network but no route to
  internal services (network policy), on top of the in-process SSRF guard.
  That belongs to steps 24 and 27.
- Prove the `FOR UPDATE` per-user limit on multi-connection Postgres in CI
  (step 25). The per-site rule no longer depends on it, thanks to the index.
