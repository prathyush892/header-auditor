# 2026-11-25: Scheduled scans and scan history (roadmap step 16)

## Plan

1. Database: store each site's next run as an absolute time
   (`sites.next_scan_at`), with an index for "what is due?" and a CHECK that
   it is set exactly when the site has a schedule.
2. Sites: keep `next_scan_at` in step with the schedule. Enabling or switching
   makes the site due now, re-sending the same schedule changes nothing, NONE
   clears it.
3. Scan history: `GET /sites/:id/scans`, newest first, keyset-paginated like
   `GET /sites`.
4. Scheduler: a pure cadence module, a `ScheduleStore` (find due sites,
   compare-and-set claim), and a tick loop that queues scans through the
   existing `ScanStore.createScan`, so the step 15 limits apply unchanged.
5. A scheduler process (`apps/api/dist/schedules/main.js`) with its own zod
   config.
6. Tests on the memory stores and on PGlite, plus one end-to-end run through
   real Redis, BullMQ and the worker.

  already-scheduled sites due, and CHECK
  `sites_next_scan_at_matches_schedule_check` (`NONE` ⇔ `NULL`, written as two

  takes an injected clock. `updateSite` runs in one transaction: a conditional
  `updateMany ... WHERE schedule <> $new` sets the schedule and

  user's site, a missing site and a malformed id all get the same
  `404 SITE_NOT_FOUND`. Unknown query params, a bad limit or a forged cursor

## Design decisions worth explaining

- **Store "next run at", not "last ran at".** The obvious design is "a site is
  due if its last scheduled scan is more than 24 h old". It works, but each
  run lands one tick later than the last, so the time drifts. It also needs a
  `NOT EXISTS` subquery per site to find due work, and it gives you nothing to
  lock on. Storing `next_scan_at` fixes all three. The next run is `due +
  interval`, so the cadence stays put. "What's due?" is an index range scan.
  And the value itself works as a claim token (next point).
- **Claiming with compare-and-set, no locks.** Two scheduler processes (a
  rolling deploy, or two replicas) can read the same due site. Each one runs
  `UPDATE sites SET next_scan_at = $next WHERE id = $id AND next_scan_at =
  $expected`. Postgres applies row updates one at a time. The first sets the
  new value; the second's `WHERE` no longer matches, so it updates 0 rows and
  skips the site. That's optimistic concurrency: no `SELECT ... FOR UPDATE`
  held across the scan creation, no advisory locks, no leader election.
  The test runs two ticks concurrently on real SQL and expects exactly one
  scan.
- **Claim first, then create: at-most-once per run.** If the process dies
  after claiming and before creating the scan, that day's scan is skipped and
  tomorrow's happens as normal. The other order (create, then advance) risks
  a duplicate instead. For a monitor, a missed daily scan is harmless;
  hitting someone's site twice is the thing to avoid. It's the same
  at-least-once vs. at-most-once trade-off as step 15, made the other way on
  purpose.
- **Scheduled scans take the same path as manual ones.** The scheduler calls
  `ScanStore.createScan(owner, site, "SCHEDULED", limits)`. That's the
  ownership check, the one-active-scan-per-site index and the per-user limit
  from step 15, with no second implementation to drift. Every outcome has a
  rule. Already running: counts as this run. User at their limit: retry in
  `SCHEDULER_RETRY_MINUTES` (never later than the next regular run). Redis
  down: mark the scan FAILED like the POST route does, then retry later.
- **Catch-up without a burst.** If the scheduler was down for three days, a
  daily site gets one scan when it comes back, and the next run is a day after
  that, not three back-to-back scans. `nextRunAfter` skips missed runs. A
  pure function with a test per edge case.
- **Defense in depth on verification.** The API already refuses to enable a
  schedule on an unverified site (step 14). The scheduler's query also
  requires `verified_at IS NOT NULL`. When step 17 can revoke verification
  (TXT record removed), scheduling stops without any extra code.
- **One unscoped query, on purpose.** Every API store method takes an owner
  id. The scheduler can't: it works for all users. So `findDueSites` is the
  one unscoped read. It returns ids only, nothing leaves the process, and each
  site's owner id goes straight back into `createScan`, which applies the
  owner-scoped checks.
- **`next_scan_at` changes only when the schedule changes.** A dashboard form
  usually re-sends every field on save. If re-sending `schedule: "daily"` made
  the site due, every rename would trigger a scan. The Prisma store makes the
  database decide (`WHERE schedule <> $new`), so there is no
  read-compare-write window. The CHECK constraint guarantees no code path can
  leave a scheduled site without a next run, or the reverse.
- **Scheduler bookkeeping doesn't touch `updated_at`.** The claim is raw SQL
  because Prisma's `update` would bump `@updatedAt`. That column means "the
  owner last edited this site", and the dashboard will show it.
- **Keyset pagination for history.** `ORDER BY created_at DESC, id DESC` with
  `WHERE (created_at, id) < cursor`, served by the existing `scans(site_id,
  created_at DESC)` index. Unlike `OFFSET`, page 50 costs the same as page 1,
  and a scan finishing mid-browse can't shift rows between pages. The id
  breaks ties between scans created in the same millisecond, and a test
  creates four with identical timestamps to prove nothing is skipped or
  repeated. The route fetches `limit + 1` rows to learn whether there's a
  next page without a `COUNT`.
- **"Empty" vs. "not yours" with one query in the common case.** The history
  query joins on `sites.owner_id`. Only when it returns zero rows does the
  store check whether the site exists for this owner, to answer `[]` or 404.
- **A separate process, safe to duplicate.** The scheduler doesn't live
  inside the API: scaling the web tier to three replicas shouldn't mean three
  schedulers. Because claims are compare-and-set, accidentally running two is
  harmless too. The loop chains `setTimeout` after each tick finishes, so
  ticks never overlap, and `stop()` waits for the running one.

## How to try it

```bash
corepack enable && pnpm install
pnpm --filter @header-auditor/api test        # 568 tests, scheduler on memory + PGlite
pnpm --filter @header-auditor/worker test     # includes the scheduled end-to-end run (needs redis-server)
pnpm build
```

Running it locally:

```bash
cp .env.example .env              # set real local passwords
docker compose up -d              # Postgres + Redis on 127.0.0.1
pnpm --filter @header-auditor/db migrate:deploy
pnpm build
set -a; . ./.env; set +a
node apps/worker/dist/main.js &                 # runs the scans
node apps/api/dist/schedules/main.js            # logs "scheduler ready", then a summary per busy tick
```

Through the API (with a session, as in earlier devlogs):

```bash
curl -s -b jar -X PATCH -H content-type:application/json -H origin:http://localhost:3000 \
  -H x-csrf-token:<csrfToken> -d '{"schedule":"daily"}' \
  http://127.0.0.1:3001/sites/<siteId>          # 409 SITE_NOT_VERIFIED until step 17; then nextScanAt = now
curl -s -b jar 'http://127.0.0.1:3001/sites/<siteId>/scans?limit=10'          # { items, nextCursor }
curl -s -b jar 'http://127.0.0.1:3001/sites/<siteId>/scans?limit=10&cursor=<nextCursor>'
```

## Next

Roadmap step 17: domain-ownership verification with a DNS TXT token, so
`verifiedAt` gets set for real and scheduling can be turned on through the
API.

Known gaps:

- **API startup wiring** is still injected (`start()` takes stores). The
  scheduler's `main.ts` now shows the full pattern for the API: config →
  Prisma → BullMQ queue. Step 17 needs a real resolver at startup anyway, so
  that's a good time to wire `start()` and the `/health/ready` checks.
- Scheduled scans of every site are due at the time the schedule was
  enabled, so many sites enabled together run together. Fine at this scale;
  with many users, add a random offset to the first run.
- The claim and the scan insert are separate transactions (at-most-once, see
  above). A transactional outbox would make claim + scan + job atomic. It
  becomes worth it if missed runs ever show up in practice.
- History has no filters yet (`trigger`, `status`, date range). The step 21
  grade chart may want `?trigger=scheduled`.
- The scheduler should run with the same restricted network as the worker
  (only Postgres and Redis), steps 24 and 27.
