# 2026-11-17: DNS checks (CAA, SPF, DMARC) (roadmap step 8)

## Plan
1. A `DnsResolver` interface with just the two lookups the checks need (TXT, CAA),
   where "no record" resolves to `[]` and only real failures reject.
2. One module per check, each split into an async `lookupX()` that gathers an
   observation and a pure `checkX()` that grades it.
3. `analyzeDns(domain)` runs all three and scores them as their own `DnsReport`
   (like the TLS and content reports), keeping the header score at Python parity.
4. Unit tests with an in-memory resolver; integration tests that point the real
   `node:dns` resolver at a tiny DNS server on 127.0.0.1.

## Built
- `dns/resolver.ts`
  - `DnsResolver` (`txt(name)`, `caa(name)`), `DnsLookupError` with a code
    (`TIMEOUT`, `SERVFAIL`, `REFUSED`, `UNREACHABLE`, `BAD_RESPONSE`).
  - `createDnsResolver({ timeoutMs, tries, servers })` on top of c-ares, with
    validated, bounded timeouts. NODATA and NXDOMAIN map to `[]`.
  - `normalizeDomain()`: trims, drops the trailing dot, lower-cases, converts IDNs
    to punycode, and rejects IP literals, single-label names and bad labels.
    `dnsTargetFromUrl()` and `parentDomains()` helpers.
- `dns/caa.ts` (10 pts): `lookupCaa()` climbs the tree (RFC 8659 §3), so
  `api.example.com` inherits `example.com`'s CAA. `checkCaa()`:
  - pass: an `issue` property restricts issuance (recommends `iodef` if missing);
  - warn (5): no `issue` (only `iodef`, or only `issuewild`, which leaves
    non-wildcard certs unrestricted), malformed issuer values, or an unknown tag
    with the critical flag set (CAs must refuse to issue);
  - warn (0): no CAA anywhere up the tree.
- `dns/spf.ts` (15 pts): a full RFC 7208 term parser (qualifiers, `ip4`/`ip6`
  validation, `/24//64` prefixes, `redirect=`/`exp=` once only, unknown
  mechanisms are permerror). `lookupSpf()` walks the `include:`/`redirect=`
  tree, counting DNS-querying terms and stopping as soon as it passes 10.
  `checkSpf()`:
  - fail: missing, more than one record, any permerror (syntax, >10 lookups,
    include of a domain with no SPF, include loop), or `+all`;
  - `-all` pass (15), `~all` warn (10), `?all` or no `all` warn (5);
  - `ptr` caps the score at 10 with a "deprecated" recommendation.
- `dns/dmarc.ts` (20 pts): tag parser (`v` must come first; `p` required;
  `sp`, `pct` (0–100), `rua`; duplicates and malformed tags rejected).
  `lookupDmarc()` checks `_dmarc.<domain>`, then the organizational domain.
  `checkDmarc()`: `p=reject` 20 (pass), `quarantine` 15, `none` 5,
  `pct<100` capped at 10, `p=reject; sp=none` capped at 10; missing, invalid or
  duplicate records fail. Subdomains inheriting the parent's record are graded on
  `sp` (falling back to `p`). Missing `rua` gets a recommendation.
- `dns/analyze.ts`: `analyzeDns(domain, { resolver, organizationalDomain })`
  returns `DnsReport` (findings, score/grade, raw observations). A failed lookup
  becomes an unscored `info` finding for that one check.
- Tests: 625 Vitest tests (was 477): 148 new across `dns-spf`, `dns-dmarc`,
  `dns-caa`, `dns-analyze` (in-memory fixture resolver that also logs every
  query) and `dns-resolver` (real c-ares against `test/helpers/dns-server.ts`,
  a ~100-line UDP DNS server on 127.0.0.1 that can answer TXT/CAA, return
  NXDOMAIN/SERVFAIL/REFUSED, or drop packets to force a timeout).
  pytest unchanged at 119. ESLint (security plugin, zero warnings), Prettier,
  `tsc`, bandit and the secrets grep are clean.
  `pnpm audit`: the known moderate `minimatch` (eslint) plus a new **high**
  `picomatch` ReDoS advisory via `typescript-eslint`. Both are dev-only lint
  tooling, never shipped or run on scan input, and picomatch has no patched
  release yet; no dependencies changed today.

## Design decisions worth explaining
- **Why these three records.** They answer two different attacks.
  *CAA* is about **certificates**: there are ~100 trusted CAs and any of them
  can issue for your domain; CAA tells them "only Let's Encrypt may", so a CA
  with sloppy validation can't be tricked into issuing for an attacker.
  *SPF and DMARC* are about **email spoofing**: SPF lists which servers may
  send mail for the domain, but it checks the hidden envelope sender, not the
  `From:` the user sees. DMARC ties the visible `From:` to SPF/DKIM and tells
  receivers what to do on failure (`reject`). That's why DMARC carries the
  most weight (20) and why SPF without DMARC isn't enough.
- **Dependency injection for the resolver.** The checks take a `DnsResolver`
  instead of calling `node:dns`. Unit tests use a fixture map (fast,
  deterministic, no network, and the query log lets tests assert *which*
  lookups happened, e.g. that SPF stops at the limit). The production resolver
  is still tested for real, against a local DNS server, so the error mapping
  isn't just assumed. Same idea as the injectable `Resolver` in the SSRF guard.
- **"No record" vs "couldn't look it up".** NXDOMAIN/NODATA are answers:
  "no DMARC" is a real finding and fails. A timeout or SERVFAIL says nothing
  about the domain, so that check becomes an unscored `info` and drops out
  of the score instead of failing; a flaky resolver shouldn't make a good
  domain look bad. Each check fails independently (`Promise.all` over
  wrappers that catch only `DnsLookupError`); a programming error still throws.
- **Lookup/grade split.** `lookupSpf()` does the I/O and returns a plain
  observation; `checkSpf()` is a pure function of it. The grading rules (the
  part that changes most) are tested without any resolver, and the API can
  store the observation and re-grade it later if the rules change.
- **SPF's 10-lookup limit is counted recursively.** RFC 7208 §4.6.4 caps
  evaluation at 10 DNS-querying terms *across the whole include tree*; at 11,
  receivers return permerror and SPF is silently ignored. Big providers'
  includes nest several levels, so counting only the top record would miss
  the most common real-world SPF breakage. The walk stops as soon as the count
  passes 10, so a hostile record can't make the scanner do unbounded queries,
  and a `visited` set catches include loops.
- **Strength, not just presence.** `+all` authorises the whole internet, so it
  fails even though a record exists. `~all` (softfail) is common and fine
  *with* DMARC enforcement, so it's a warn, not a fail. `p=none` only monitors.
  `pct=50` only applies the policy to half the failing mail. `sp=none` leaves
  every subdomain spoofable even when `p=reject`.
- **Tree climbing and inheritance.** Both CAA and DMARC look beyond the exact
  name: CAA climbs to the closest ancestor with records (stopping before the
  TLD); DMARC falls back to the organizational domain and then applies `sp`.
  Scanning `www.example.com` without this would report "missing" for records
  that actually protect it.
- **Input validation before any query.** `normalizeDomain()` runs first:
  punycode for IDNs (so `bücher.example` is what the DNS actually sees), length
  and label rules, and IP literals rejected (they have no TXT/CAA). DNS checks
  never connect to the target, so there's no SSRF surface, but the queries
  still go to the configured resolver, so garbage input is rejected up front.
- **No regex backtracking.** The ESLint security plugin flagged the first
  versions of the SPF mechanism and CAA issuer regexes as potentially unsafe.
  They're now small hand-written splitters with simple, anchored regexes, since
  record contents are attacker-controlled input.

## How to try it
```bash
corepack enable && pnpm install
pnpm check                                               # lint + format + tsc + 625 tests
pnpm --filter @header-auditor/core exec vitest run dns   # just the DNS tests
cd cli-python && pytest -q                               # 119 tests
```

```ts
import { analyzeDns, checkSpf, lookupSpf, type DnsResolver } from "@header-auditor/core";

// Pure: grade fixture records, no network.
const zone: Record<string, string[]> = {
  "example.test": ["v=spf1 include:_spf.mail.test ~all"],
  "_spf.mail.test": ["v=spf1 ip4:192.0.2.0/24 -all"],
};
const resolver: DnsResolver = {
  txt: async (name) => zone[name] ?? [],
  caa: async () => [],
};
console.log(checkSpf(await lookupSpf("example.test", resolver)).status); // warn (~all)

const report = await analyzeDns("example.test", { resolver });
console.log(report.grade, report.findings.map((f) => `${f.check}: ${f.status}`));
// Without `resolver`, analyzeDns uses the system resolver (createDnsResolver()).
```

Known gaps to pick up later:
- The organizational domain is "last two labels" unless one is passed in; wrong
  for `example.co.uk`. A Public Suffix List lookup would fix it (likely in the
  worker, which can keep the list up to date).
- SPF: `a`/`mx` sub-lookups and the RFC's "void lookup" limit (2) aren't counted,
  and macro includes (`%{i}`) can't be followed statically (reported as incomplete).
- DKIM isn't checked: selectors aren't discoverable from DNS alone.
- DNSSEC isn't validated; MTA-STS / TLS-RPT would be natural next email checks.
- Dev-only advisories (`minimatch` via eslint, `picomatch` via typescript-eslint)
  clear when those packages bump their dependencies.
