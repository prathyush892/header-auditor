# 2026-11-27: The dashboard app: Next.js shell, sign-in pages, typed API client (roadmap step 18)

## Plan

1. `apps/web`: Next.js 15 (App Router) + TypeScript + Tailwind 4 as a new
   workspace package, wired into the root lint/format/typecheck/test/build.
2. How the browser reaches the API: a same-origin `/api/*` proxy (Next.js
   rewrites), so the httpOnly session cookie and the CSRF checks from step 13
   work unchanged and the API needs no CORS.
3. A typed client: zod-validated responses, CSRF token in memory, timeouts,
   three error classes.
4. Session context, `/login` and `/register`, a guarded app shell with sign
   out, and middleware that sends obviously signed-out visitors to `/login`.
5. Tests: unit tests, plus a contract test running the client against the
   real API on 127.0.0.1, plus a manual browser smoke test.

    `/login?next=<path>`.
- **Typed API client** (`src/lib/api/`):
  - `createApiClient({ baseUrl, fetch?, timeoutMs?, onUnauthorized? })` with
    `health`, `register`, `login`, `session`, `logout`, `logoutAll`.
  - Every success body goes through a zod schema (`schemas.ts`). Every error
    body is parsed as the API's `{ error: { code, message, requestId,
    details } }`.
  - Failures are `ApiError` (has `status`, `code`, `requestId`, `details`,
    `retryAfterSeconds`), `ApiNetworkError` (`timedOut`) or
    `ApiResponseError` (an answer we don't understand).
  - Requests: `credentials: "same-origin"`, `cache: "no-store"`,
    `redirect: "error"`, 15 s timeout combined with the caller's
    `AbortSignal`. Paths are checked against an allow-list pattern.
  - CSRF: the token from login/register/session is kept in a closure and sent
    as `x-csrf-token` on POST/PUT/PATCH/DELETE only. On `403
    CSRF_TOKEN_INVALID` the client refetches `/auth/session` and retries
    once.

## Design decisions worth explaining

- **A same-origin proxy instead of calling the API cross-origin.** The
  browser only ever talks to the dashboard's origin. `/api/*` is forwarded
  by Next.js server-side. So the session cookie is a first-party cookie on
  the dashboard's host, `SameSite=Lax` and the `__Host-` prefix work as
  designed, and the API needs no CORS (no `Access-Control-Allow-Credentials`
  to get wrong). The API's CSRF origin check still works because the proxy
  passes the browser's `Origin` header through unchanged. The cost is one
  extra hop, which is negligible next to a scan.
- **The CSRF token lives in memory, not in localStorage.** Anything in
  localStorage can be read by any script on the page, including an injected
  one, and stays there after sign-out. A token in a closure is gone on
  reload, and `GET /auth/session` gives it back (the API derives it from the
  session, so it's the same value). A cross-site attacker can't make that
  call read the token, because the same-origin policy hides the response.
- **The session cookie is invisible to the dashboard, and that's the point.**
  It's httpOnly, so even an XSS bug can't steal it. The dashboard learns who
  is signed in only by asking the API. Middleware checks only whether a
  cookie exists. That's a UX shortcut (no flash of the app shell for
  signed-out visitors), not access control; a forged cookie gets past it and
  then gets a 401 from the API. Authorization lives in exactly one place.
- **Runtime validation of API responses.** TypeScript types vanish at
  runtime. If the API renames a field, a type-only client would happily
  render `undefined`. zod parsing turns that into an explicit
  `ApiResponseError`. The contract test runs those schemas against the real
  API, so drift shows up in CI. I chose this over importing the API's types:
  the web bundle stays independent of Fastify, and the test checks real
  JSON, which a shared type can't.
- **Retrying a CSRF failure once is safe.** The API checks the token in a
  `preHandler` hook, before the route handler runs, so a 403 there means
  nothing happened on the server. A stale token is the normal result of
  signing in again in another tab (new session, new token). Refetch, retry
  once, and if it fails again, show the error. No loop.
- **Open-redirect protection on `?next=`.** Sending users back where they
  were going is good UX. Taken at face value it's a phishing tool:
  `/login?next=https://evil.example` would bounce a freshly signed-in user to
  a fake page that looks like part of our flow. `safeNextPath` only accepts
  rooted paths, rejects `//host` and `/\host` (browsers treat both as
  another host), control characters and backslashes, then parses against a
  placeholder origin and checks the origin didn't change.
- **Client-side validation is UX, not security.** The form checks mirror
  the API's rules so users see problems instantly, but the API validates
  everything again and its answer wins. That's also why the client sends
  exactly `{ email, password }` and nothing else from its input.
- **One message for "no such user" and "wrong password".** The API already
  does this to prevent account enumeration. The UI keeps it that way instead
  of "helpfully" guessing which one it was.
- **The dashboard's own headers.** `poweredByHeader: false` because our own
  scanner flags `X-Powered-By`. Framing is denied twice (`X-Frame-Options`
  for old browsers, CSP `frame-ancestors` for new ones), which stops
  clickjacking on the sign-in form. A full nonce-based CSP is deliberately
  left for step 24, where the scanner audits the dashboard itself in CI.
- **One canonical origin.** The API's `API_ALLOWED_ORIGINS` and the cookie's
  host must agree with the URL people open. In dev that's
  `http://localhost:3000` (not 127.0.0.1, which is a different origin and
  would also be a different cookie jar).

## How to try it

```bash
corepack enable && pnpm install
pnpm --filter @header-auditor/web test      # 130 tests, incl. the real API on 127.0.0.1
pnpm build                                  # includes `next build`

# Dashboard against an in-memory API (no Docker needed):
pnpm --filter @header-auditor/web dev:api   # API on 127.0.0.1:3001
pnpm --filter @header-auditor/web dev       # open http://localhost:3000
```

Then: open `/dashboard` (you land on `/login`), create an account with a
15+ character passphrase, sign out, try a wrong password, and try
`/login?next=https://example.com/` (you end up on `/dashboard`).

Through the proxy with curl:

```bash
curl -s -c jar -H origin:http://localhost:3000 -H content-type:application/json \
  -d '{"email":"ada@example.com","password":"correct horse battery staple"}' \
  http://localhost:3000/api/auth/register
curl -s -b jar http://localhost:3000/api/auth/session | jq .user
curl -sI http://localhost:3000/login | grep -i -E 'x-frame|content-security|x-powered'
```

Known gaps:

- **Client IPs behind the proxy.** The API sees every request coming from
  the Next.js server. With `API_TRUST_PROXY=false` (the default), the
  per-IP login and register limits become one shared bucket for all users.
  Turning `API_TRUST_PROXY` on isn't enough by itself: I checked, and
  Next.js forwards a client-supplied `X-Forwarded-For` unchanged, so a
  client could pick its own "IP". The fix belongs with deployment (step
  27): the edge proxy overwrites `X-Forwarded-For`, and the API trusts
  exactly that hop.
- `API_INTERNAL_URL` is baked into the rewrite at `next build`. Changing it
  needs a rebuild (documented in `.env.example`). A standalone Docker image
  (step 27) will need it as a build argument or a runtime proxy.
- No password reset, email verification or session list in the UI yet.
- The sign-in pages render the form while the session check is in flight,
  then redirect if you were already signed in, which can flash briefly.
- No component tests yet: forms are covered by unit tests of their logic and
  the manual browser run. The Playwright end-to-end test is step 26.
- `docker-compose.yml` doesn't run the dashboard yet (step 27).
