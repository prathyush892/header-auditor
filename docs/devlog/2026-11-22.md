# 2026-11-22: Auth (roadmap step 13)

## Plan

1. `packages/db`: a `Session` table. The cookie carries a random token, the
   database stores only its SHA-256.
2. `apps/api/src/auth`: argon2id hashing and a password policy, session and
   CSRF tokens, a rate limiter, and an `AuthStore` interface with in-memory
   and Prisma implementations.
3. Routes: register, login, logout, logout-all, current session; a
   `requireAuth()` helper for the sites routes in step 14.
4. Hooks for every route: Origin check on unsafe methods, session cookie to
   `request.auth`, CSRF token check.
5. Config for allowed origins, cookie security, session lifetimes and rate
   limits, validated like the rest of the API config.
6. Tests at every layer, including the Prisma store against a real (PGlite)
   Postgres on 127.0.0.1.

## Built

- **Migration `20261122000000_sessions`**: `sessions(id, user_id, token_hash
  CHAR(64) UNIQUE, created_at, last_seen_at, expires_at, user_agent)`,
  cascade on user delete, indexes on `user_id` and `expires_at`. Hand-written
  CHECKs: `token_hash` must be lower-case hex SHA-256, and `expires_at >
  created_at`.
- **`auth/password.ts`**: argon2id via `@node-rs/argon2` (prebuilt binaries,
  no node-gyp) with OWASP parameters (m=19 MiB, t=2, p=1). Passwords are
  NFC-normalised. `needsRehash()` spots hashes made with old parameters.
  `burn()` runs a throwaway verification for unknown emails. Policy (applied
  at registration only): 15-128 code points, not only whitespace, not one
  repeated character, not the email address.
- **`auth/tokens.ts`**: 32-byte base64url session tokens; `SHA-256` for
  storage; CSRF token = `HMAC-SHA256(key = session token, "csrf:v1")`,
  checked with `timingSafeEqual`.
- **`auth/rate-limit.ts`**: `MemoryRateLimiter`, a fixed-window counter with
  an injectable clock. It tracks at most 100k keys (expired keys go first,
  then the oldest), and the interface is async so Redis can replace it.
- **`auth/store.ts` / `auth/prisma-store.ts`**: the `AuthStore` interface,
  `MemoryAuthStore`, and `createPrismaAuthStore(client)`. The Prisma store
  types the client structurally, so the API build doesn't import the
  generated client. It turns Prisma's `P2002` into `EmailTakenError`.
- **`auth/plugin.ts`** (`registerAuth`, enabled by `buildApp({ auth })`):
  - `POST /auth/register`: 201, logged in, `409 EMAIL_TAKEN`, 400 with
    `details[].path = "password"` for policy failures.
  - `POST /auth/login`: 200, or `401 INVALID_CREDENTIALS` (the same body for
    an unknown email and a wrong password), or `429 RATE_LIMITED` with
    `Retry-After`.
  - `POST /auth/logout` (always 204), `POST /auth/logout-all`,
    `GET /auth/session` (user, `csrfToken`, `expiresAt`, `idleExpiresAt`).
  - Cookie `__Host-ha_session`: `HttpOnly; Secure; SameSite=Lax; Path=/`,
    no `Domain`, `Max-Age` = absolute TTL. With `AUTH_COOKIE_SECURE=false`
    (plain-http dev only) it is named `ha_session`.
  - The default content-type parser for `text/plain` is removed, so
    form-style bodies get 415.
- **Config**: `API_ALLOWED_ORIGINS` (normalised through `URL`, de-duplicated,
  paths, credentials, wildcards and non-http schemes rejected),
  `AUTH_COOKIE_SECURE` (refused as false in production),
  `AUTH_SESSION_TTL_HOURS` (7 days by default), `AUTH_SESSION_IDLE_MINUTES`
  (12 h, must not exceed the TTL), `AUTH_RATE_LIMIT_WINDOW_SECONDS` /
  `_PER_ACCOUNT` / `_PER_IP` (15 min, 10, 100). All are documented in
  `.env.example`.
- **Tests**: api 126 → 267 (auth routes 45, store contract 17 running on
  both stores, password 20, tokens 21, rate limiter 9, config +28, and a

## Design decisions worth explaining

- **Why argon2id, and why these numbers.** Password hashes get stolen, and
  then the attacker guesses offline. argon2id is memory-hard: each guess
  needs about 19 MiB of RAM, which wipes out most of a GPU's parallelism.
  bcrypt and PBKDF2 are only CPU-hard. The parameters are OWASP's
  recommendation. The encoded hash records them, so raising them later is
  safe: old hashes still verify, and `needsRehash()` upgrades each one the
  next time that user logs in, while the plaintext is in memory.
- **Unknown email vs wrong password.** Both return the same status, code and
  message. If unknown emails returned instantly, response timing would tell
  an attacker which emails have accounts (account enumeration). So the
  unknown-email path still runs an argon2 verification against a dummy hash.
  Registration does admit "email taken" with a 409. Avoiding that needs an
  email-verification flow, which is listed under Next.
- **Server-side sessions over JWTs.** The cookie holds 256 random bits and
  the server keeps the state. Logout and "log out everywhere" take effect
  immediately: delete the row. A stateless JWT stays valid until it
  expires, unless you build a revocation list, which is a session table
  again.
- **Only the token's hash is stored.** If the `sessions` table leaks
  (backup, SQL injection elsewhere), the attacker gets hashes they can't use
  as cookies. A fast SHA-256 is fine here, unlike for passwords: the input
  is 256 random bits, so there's nothing to brute-force. The database's
  CHECK constraint means a bug that writes the raw token fails loudly.
- **Cookie attributes, one by one.** `HttpOnly`: page JavaScript (including
  XSS) can't read the token. `Secure`: never sent over plain http.
  `SameSite=Lax`: not sent on cross-site POSTs, a first CSRF layer.
  `__Host-` prefix: the browser refuses the cookie unless it is Secure,
  `Path=/` and has no `Domain`, so a compromised sibling subdomain can't
  plant or overwrite it ("cookie tossing").
- **CSRF in three layers.** SameSite has gaps: same-site subdomains count,
  and older browsers ignore it. So:
  1. **Origin allow-list** on every POST/PUT/PATCH/DELETE. Browsers send
     `Origin` on these. `Sec-Fetch-Site` is the fallback, and only
     `same-origin`/`none` pass, which also blocks sibling subdomains. A
     request with neither header doesn't come from a browser page, so it
     can't be a CSRF and is allowed (curl, the CLI).
  2. **JSON only.** A cross-site `<form>` can only send urlencoded,
     multipart or text/plain bodies without a CORS preflight. Fastify
     accepts text/plain by default, so that parser is removed and all three
     get 415.
  3. **Per-session token** (synchronizer pattern) on authenticated unsafe
     requests. It is `HMAC(session token, "csrf:v1")`: an attacker can't
     compute it without the httpOnly cookie, and it needs no extra server
     secret or database column. The dashboard reads it from
     `/auth/session` and sends it as `x-csrf-token`. Login and register are
     exempt (there's no session yet). Layers 1 and 2 protect them, which also
     stops login CSRF (being silently logged into the attacker's account).
- **Session fixation.** Every login creates a new token and deletes the
  session the request came in with. An attacker who planted a known cookie
  before login gets nothing.
- **Two expiries.** The idle timeout (12 h) limits a forgotten browser. The
  absolute TTL (7 days) limits a stolen cookie even if it's in constant use.
  A test drives an injected clock through both. `lastSeenAt` is written at
  most once a minute, so each request doesn't cost a database write.
  Expired rows are deleted when presented and swept hourly.
- **Rate limiting by IP and by account.** Per-IP limits stop one machine
  spraying many accounts. Per-account limits stop a botnet hammering one
  account from many IPs. The limit is checked before argon2 runs, so floods
  can't turn the hash into a CPU DoS. A successful login resets that
  account's counter. Trade-off: anyone can lock an account for 15 minutes by
  failing logins (temporary, not permanent). This is also why
  `API_TRUST_PROXY` defaults to off: if `X-Forwarded-For` were trusted
  without a proxy, every request could claim a new IP.
- **Fixed window, in memory, bounded.** It's simple and predictable, and
  good enough for login throttling. Counters are per process. With more
  than one API instance they belong in Redis, and the async `RateLimiter`
  interface is there for that. The map is capped at 100k keys, so a flood
  of random emails can't exhaust memory.
- **One contract, two stores.** The routes only know `AuthStore`. The same
  test suite runs against the in-memory store and the Prisma store on a
  real Postgres (PGlite). That caught a real bug today: the in-memory
  `createUser` awaited between "check email" and "insert". Two concurrent
  registrations both succeeded there, while Postgres's unique index
  correctly refused one.
- **Config guard rails.** `AUTH_COOKIE_SECURE=false` crashes at boot in
  production. Allowed origins are normalised the same way browsers
  serialise `Origin`, so `https://App.example.com:443` matches. Wildcards
  and paths are rejected: with CSRF, a too-permissive allow-list is the
  vulnerability.

## How to try it

```bash
corepack enable && pnpm install
pnpm --filter @header-auditor/api test        # 267 tests (PGlite on 127.0.0.1 for the Prisma store)
pnpm --filter @header-auditor/db test         # 99 tests incl. the sessions migration
```

In code (the server doesn't open a database connection yet, see Next):

```ts
import { buildApp, loadConfig, MemoryAuthStore, createPrismaAuthStore, requireAuth } from "@header-auditor/api";
import { createPrismaClient } from "@header-auditor/db";

const app = await buildApp({
  config: loadConfig(),
  auth: { store: createPrismaAuthStore(createPrismaClient()) }, // or new MemoryAuthStore()
});
app.post("/sites", (request) => ({ owner: requireAuth(request).user.id }));
```

Against a running app (with `AUTH_COOKIE_SECURE=false` for plain http):

```bash
curl -i -c jar -H 'content-type: application/json' -H 'origin: http://localhost:3000' \
  -d '{"email":"me@example.test","password":"a long enough passphrase"}' http://127.0.0.1:3001/auth/register
curl -s -b jar http://127.0.0.1:3001/auth/session          # -> { user, csrfToken, ... }
curl -i -b jar -X POST http://127.0.0.1:3001/auth/logout   # 403 CSRF_TOKEN_INVALID
curl -i -b jar -X POST -H "x-csrf-token: <csrfToken>" http://127.0.0.1:3001/auth/logout   # 204
```
