# 2026-11-26: Domain-ownership verification with a DNS TXT record (roadmap step 17)

## Plan

1. A pure verification module in the API: which record name, which value, and
   how a TXT answer is judged. DNS goes through `packages/core`'s
   `DnsResolver`, so tests inject answers.
2. `SiteStore.recordVerification()`: one conditional update, on both stores.
3. `POST /sites/:id/verify`, owner-scoped, CSRF-protected, rate-limited per
   account, with an error code for each way a check can fail.
4. Config for the resolver (servers, timeout) and the rate limit.
5. Tests: unit, both stores, HTTP on memory + PGlite, and the real c-ares
   resolver against a DNS server on 127.0.0.1.

## Built

- **`apps/api/src/verification/`**:
  - `verificationRecord(siteUrl, token)` → `{ name, type: "TXT", value }`,
    e.g. `_header-auditor-challenge.www.example.com` with value
    `header-auditor-verification=<64 hex chars>`. The hostname goes through
    core's `normalizeDomain` (lower-case, punycode for IDNs). IP literals,
    `localhost` and single-label hosts throw `VerificationUnsupportedError`.
  - `evaluateTxtRecords(records, record)` → `VERIFIED`, `RECORD_MISSING` (no
    record with our prefix) or `TOKEN_MISMATCH` (our prefix, another token).
    Any exact match verifies. Whitespace around the value is ignored; nothing
    else is. At most 50 TXT strings are looked at.
  - `createDomainVerifier(resolver)`: a `DnsLookupError` (timeout, SERVFAIL,
    refused) becomes `DNS_ERROR`, never a verdict. Any other error is thrown.
  - `createVerifierFromConfig(config)`: the production verifier (c-ares with
    the configured servers and timeout).
- **Store**: `recordVerification(ownerId, id, token, at)`. The Prisma version
  is one `updateMany ... WHERE id, owner_id, verification_token = $token AND
  verified_at IS NULL`, then a read. The memory store does the same.
- **Route** `POST /sites/:id/verify`:
  - Not your site, missing, or malformed id → `404 SITE_NOT_FOUND`, same as
    the other site routes.
  - Already verified → `200` with the site, no DNS query.
  - More than `SITES_VERIFY_ATTEMPTS_PER_WINDOW` checks per account per
    window → `429 RATE_LIMITED` with `Retry-After`, before any lookup.
  - `422 VERIFICATION_RECORD_MISSING` / `VERIFICATION_TOKEN_MISMATCH`, with
    a message naming the exact record and value to publish.
  - `422 VERIFICATION_UNSUPPORTED` for IP/localhost sites (dev mode only).
  - `503 VERIFICATION_DNS_UNAVAILABLE` when the lookup fails (generic
    message to the client, details in the log).
  - Success → `200` with `verified: true`. `PATCH { schedule: "daily" }`
    now works through the API, and the step 16 scheduler picks the site up.
  - Each check logs `{ userId, siteId, outcome, record }`.
  - Only registered when `sites.verification` is passed to `buildApp`.
    `start()` warns when it isn't.
- **Public site JSON** has a new `verificationRecord` field
  (`{ name, type, value }`, or null when the host can't be verified), so the
  dashboard (step 19) can show copy-paste instructions.
- **Config** (documented in `.env.example`):
  `SITES_VERIFY_ATTEMPTS_PER_WINDOW` (10), `SITES_VERIFY_WINDOW_SECONDS`
  (600), `SITES_VERIFICATION_DNS_SERVERS` (empty = system resolver;
  comma-separated IPs with optional ports, hostnames refused),
  `SITES_VERIFICATION_DNS_TIMEOUT_MS` (3000).
- `@header-auditor/core` is now a dependency of the API (workspace link; no
  new third-party packages).
- **Tests**: api 568 → 653. Verification module 32 (including the real

## Design decisions worth explaining

- **Why verify at all.** A scheduled scan is our server sending traffic to
  someone's site every day, forever. Without proof of ownership, anyone
  could sign up and point the scanner at a site they don't own. The scanner
  would then be a free, persistent probe against third parties. A manual,
  one-off scan is closer to "visit the site once". A recurring job needs the
  owner's consent, and controlling DNS is good evidence of that.
- **Why DNS TXT, not a file at `/.well-known/`.** An HTTP file proves you can
  put content on the web server, which also covers anyone with an upload
  feature or a compromised CMS. A TXT record proves you can edit the zone,
  which is the actual owner. It also works for sites that don't serve the
  file path (redirects, SPAs, CDNs). Let's Encrypt, Google Search Console
  and GitHub all offer DNS verification for the same reason.
- **An underscore name, not the bare hostname.** `_header-auditor-challenge.
  <host>` follows RFC 8552 (like `_acme-challenge` and `_dmarc`). It can't
  clash with a real hostname. It doesn't crowd the apex TXT set, where SPF
  lives and where some providers cap the number of records. And it works
  even when `<host>` is a CNAME, because a CNAME can't have other records
  beside it, but a child name can.
- **Exact host, no inheritance.** Verifying `www.example.com` doesn't verify
  `example.com` or `api.example.com`, and a record at the parent doesn't
  cover children. That's stricter than it has to be for big organisations.
  But on shared hosts (`alice.pages.example`), controlling one subdomain
  must never let you claim the parent or the neighbours. Inheritance can be
  added later as an explicit "verify the whole domain" option.
- **The token is per site, not per domain.** Two accounts can add the same
  URL. Each site gets its own random 32-byte token, so Alice's record proves
  nothing for Bob's site. A test checks exactly that, and that both can
  verify with two records side by side.
- **Comparing against the token we looked up.** The store's update is
  conditional on `verification_token = $token AND verified_at IS NULL`.
  That's compare-and-set again (as in step 16). If the token were ever
  rotated between the DNS lookup and the write, the old record can't mark
  the new token verified. And two concurrent checks can't overwrite each
  other's timestamp, so the first verification time is kept.
- **"Couldn't check" is not "failed".** A DNS timeout or SERVFAIL says
  nothing about ownership, so it gets a 503 (try again later), not a 422 (you
  did it wrong). The core DNS checks follow the same rule: a flaky resolver
  isn't evidence of a misconfiguration.
- **Rate limit per account, checked before the lookup.** Every check sends a
  DNS query for a name the user picked. Without a limit, the API can be used
  to generate DNS traffic. The limit is per account, not per site, because
  adding more sites must not add more budget. It's checked before the
  lookup, so a blocked request costs nothing. Requests for sites you can't
  see return 404 before the limiter, so they don't use up your attempts.
- **Verification is only as honest as the resolver.** An attacker who can
  spoof DNS answers to our server can fake a verification. That's why
  `SITES_VERIFICATION_DNS_SERVERS` exists: point it at a validating resolver
  you trust. It only takes IP addresses, because looking up the resolver's
  own hostname would need a resolver. The 127.0.0.1 test server goes through
  the same setting, so the production code path is what gets tested.
- **No revocation (yet).** Once verified, a site stays verified. Removing
  the record later changes nothing. That's a deliberate scope cut. Revoking
  on one failed lookup would stop someone's monitoring during a DNS
  migration. Doing it properly needs periodic re-checks with a grace period
  (see Next). The scheduler already requires `verified_at IS NOT NULL`, so
  when revocation exists, scheduling stops by itself.
- **Errors that tell you what to do.** The 422 message names the exact
  record and value. The site JSON includes `verificationRecord`, so the
  dashboard can show it before the first attempt. Each failure has its own
  error code, so the UI can branch without parsing messages.

## How to try it

```bash
corepack enable && pnpm install
pnpm --filter @header-auditor/api test        # 653 tests, incl. a local DNS server on 127.0.0.1
pnpm build
```

Through the API (with a session, as in earlier devlogs):

```bash
curl -s -b jar http://127.0.0.1:3001/sites/<siteId> | jq .verificationRecord
# { "name": "_header-auditor-challenge.example.com", "type": "TXT",
#   "value": "header-auditor-verification=<token>" }

# Publish that TXT record at your DNS provider, then:
curl -s -b jar -X POST -H origin:http://localhost:3000 -H x-csrf-token:<csrfToken> \
  http://127.0.0.1:3001/sites/<siteId>/verify        # 422 until the record is visible, then 200
curl -s -b jar -X PATCH -H content-type:application/json -H origin:http://localhost:3000 \
  -H x-csrf-token:<csrfToken> -d '{"schedule":"daily"}' \
  http://127.0.0.1:3001/sites/<siteId>               # 200 now, nextScanAt = now
```

`dig +short TXT _header-auditor-challenge.example.com` shows what the API
will see (modulo caching).

## Next

API client.

Known gaps:

- **Re-verification and revocation**: re-check verified sites from the
  scheduler (say weekly). After N failed checks in a row over a grace
  period, clear `verified_at` and the schedule, and tell the owner (step 23
  alerts).
- **API startup wiring** is still injected (`start()` takes stores). The
  verifier is now ready for it (`createVerifierFromConfig(config.sites.
  verification)`); wiring Prisma, BullMQ and the verifier into `server.ts`
  remains open.
- The verification rate limiter is in-process, like the login limiter. With
  several API replicas it needs the Redis-backed version.
- No token rotation endpoint yet. The store's token-conditional update
  already makes adding one safe.
