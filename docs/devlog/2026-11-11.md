# 2026-11-11: First checks in the TypeScript engine (roadmap step 2)

## Plan

2. Port three checks: HSTS, X-Content-Type-Options, Referrer-Policy, with identical
   scores, weights and messages.
3. Mirror the Python unit tests in Vitest, and add a shared JSON table of cases that
   *both* test suites run, so the engines can't drift apart.
4. Keep everything pure (no network): fetching arrives in step 5.

## Built
- `packages/core/src/finding.ts`: `Finding` type, `Status` enum-like const and
  `makeFinding()`, which freezes the result and rejects impossible scores
  (`score > weight`, negatives, non-integers).
- `packages/core/src/headers.ts`: `HeaderMap`, a case-insensitive, multi-value header
  view. Builds from `[name, value]` pairs, a plain record, or a WHATWG `Headers` object
  (what `fetch` returns). Validates names (RFC 9110 token) and rejects CR/LF/NUL in values.
- `packages/core/src/checks/`: `checkHsts`, `checkContentTypeOptions`,
  `checkReferrerPolicy`, plus small exported helpers (`parseMaxAge`,
  `effectiveReferrerPolicy`) so the parsing logic is tested on its own.
- `spec/parity/checks.json`: 25 shared cases (status/score/weight). Run by
  `packages/core/test/parity.test.ts` **and** `cli-python/tests/test_parity.py`.
- **Bug fix in the Python engine**, found by the parity table on its first run:
  `Referrer-Policy: ,` (present but with no tokens) crashed with `IndexError`. Both
  engines now return a WARN ("browser default applies").
- Tests: 59 Vitest tests (was 2) and 39 pytest tests (was 14), all green; ESLint
  (security rules, zero warnings), Prettier, `tsc`, bandit and `pnpm audit --audit-level=high` clean.

## Design decisions worth explaining
- **A shared, language-neutral spec instead of two hand-written test suites.** When you
  port code, the risk is quiet divergence: someone tweaks a score in one engine only.
  Putting the expected outcomes in one JSON file that both pytest and Vitest execute
  turns "keep them in sync" from a promise into a CI failure. It paid off immediately by
  finding a real crash in the Python code.
- **`HeaderMap`, not `Headers`.** The global WHATWG `Headers` class joins repeated
  headers with `", "`. That breaks `Set-Cookie`, because cookie `Expires` dates contain
  commas, so you can't split them back reliably. `HeaderMap` stores each value
  separately and reads cookies via `Headers.getSetCookie()`. A different name also avoids
  shadowing the global and confusing readers.
- **Validate input at the boundary.** Header names must be RFC 9110 tokens, and values
  containing CR/LF/NUL are rejected. In a scanner those values come from untrusted
  servers and later get rendered in reports and dashboards. Rejecting malformed input
  early is cheaper than escaping it correctly everywhere downstream (header/log injection).
- **`max-age` parsed as `BigInt`.** Servers sometimes send absurd values. `Number`
  would lose precision past 2^53 (`Number.MAX_SAFE_INTEGER`), and printing it would show
  `1e+24`. `BigInt` compares exactly and prints the same digits Python's arbitrary-size
  `int` prints, so the two engines produce identical messages.
- **Invariants enforced in one constructor.** Every finding goes through `makeFinding()`,
  which throws on `score > weight`. A bad check fails a unit test loudly instead of
  quietly inflating a grade. The result is frozen, so nothing downstream can change it.
- **Parity over "improvements" for now.** Some Python behaviour is simplistic, for example
  `includeSubDomains` is a substring match. I kept it identical on purpose: step 4's goal
  is parity, and behaviour changes should land in both engines together, with a parity case.

## How to try it
```bash
corepack enable && pnpm install
pnpm check                                   # lint + format + tsc + vitest (59 tests)
pnpm --filter @header-auditor/core test parity      # only the shared cases
cd cli-python && pytest -q tests/test_parity.py     # same cases on the Python engine
```

```ts
import { HeaderMap, checkHsts } from "@header-auditor/core";
checkHsts(new HeaderMap({ "Strict-Transport-Security": "max-age=100" }));
// { check: "Strict-Transport-Security", status: "warn", score: 10, weight: 20, ... }
```
