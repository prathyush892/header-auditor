# 2026-11-20: Database schema + local Postgres/Redis (roadmap step 11)

## Plan

1. New workspace package `packages/db`: Prisma 7 schema for User, Site, Scan,
   Finding, AlertRule, modelled on what the engine already produces
   (`Finding` = check/status/detail/weight/score/recommendation, `Grade` A-F).
2. First migration, plus hand-written CHECK constraints for the invariants
   Prisma can't express.
3. A small typed surface for the API and worker: validated `DATABASE_URL`,
   a client factory, and engine -> row mappers.
4. `docker-compose.yml` with Postgres and Redis, safe by default.
5. Tests that run the real migration against a real Postgres without Docker.

## Built

- `packages/db/prisma/schema.prisma`
  - `users`, `sites`, `scans`, `findings`, `alert_rules` (snake_case tables
    and columns via `@@map`/`@map`, UUID primary keys, `timestamptz(3)`).
  - Enums: `Grade`, `FindingStatus`, `FindingCategory` (HEADERS, TLS,
    CONTENT, DNS, WELL_KNOWN), `ScanStatus`, `ScanTrigger`, `ScanSchedule`,
    `AlertKind` (GRADE_DROP, CERT_EXPIRY), `AlertChannel` (EMAIL, WEBHOOK).
  - Every foreign key is `ON DELETE CASCADE` down the chain
    User -> Site -> Scan -> Finding and Site -> AlertRule.
  - Indexes chosen for the queries the roadmap needs: `(site_id, created_at
    DESC)` for scan history, `scans.status` for the worker,
    `(scan_id, check)` for the diff view, `(owner_id, url)` unique per owner.
  - `Site` already has `verificationToken`/`verifiedAt` (step 17),
    `schedule` (step 16) and `firstPartyHosts` (feeds the SRI check from
    step 10).
- `prisma/migrations/20261120000000_init/migration.sql`: generated-style DDL
  plus a marked block of 11 CHECK constraints: lower-case emails, verification
  token length >= 32, `http(s)://` site URLs only, score 0-100, HTTP status
  100-599, "succeeded scan has score + grade + finished_at", "failed scan has
  an error", `finished_at >= started_at`, `0 <= score <= weight` (same as
  `makeFinding()`), non-negative positions, and `cert_expiry_days` required
  (1-365) only for CERT_EXPIRY rules. `migrations/README.md` documents the
  convention.
- `packages/db/src`
  - `parseDatabaseUrl()` / `redactDatabaseUrl()`: postgres(ql):// only, host
    and exactly one database name required; errors never contain the password.
  - `createPrismaClient()`: Prisma 7 client over the `pg` driver adapter, with
    validated pool size and connect timeout.
  - `findingRows()`, `toDbFindingStatus()`, `toDbGrade()`, `toDbScore()`:
    engine results -> rows, validated, positions numbered across report
    sections, NUL bytes stripped.
- `docker-compose.yml`: `postgres:17-alpine` and `redis:7.4-alpine`, ports
  bound to `127.0.0.1` only, passwords required (`${VAR:?}`, no defaults),
  SCRAM auth for Postgres, Redis `requirepass` + AOF + `noeviction`,
  healthchecks, named volumes, `no-new-privileges`.
- `.env.example`: placeholder POSTGRES_*, REDIS_*, DATABASE_URL, REDIS_URL.
- CI: `prisma validate` and `docker compose config` steps; the Prisma client
  is generated by the db package's `postinstall` during `pnpm install`.
- `pnpm-workspace.yaml`: override `effect` to 3.22.5. `@prisma/config` pins
  3.20.0, which has a high-severity ReDoS advisory (GHSA-7589-6fvf-x4pw) and
  would have failed the `pnpm audit --audit-level=high` CI gate.
- Tests: 92 new Vitest tests in `packages/db` (878 TS total, core unchanged at
  786); pytest unchanged at 119. ESLint (security plugin), Prettier, `tsc`,
  bandit and the secrets grep are clean. `pnpm audit`: no high/critical; the
  dev-only moderate `minimatch` (via eslint) remains.
  - `migration.test.ts`: applies the migration to PGlite, checks the tables,
    that Postgres enum labels equal the generated client's enums, that every
    FK cascades, that each CHECK rejects bad rows and accepts good ones, and
    that deleting a user removes exactly their data.
  - `client.test.ts`: the real `createPrismaClient()` connects over the
    Postgres wire protocol to PGlite on 127.0.0.1 and round-trips a scan with
    findings and a JSON report, scan history paging, owner scoping, P2002 on
    duplicates, CHECK violations and cascades.
  - `compose.test.ts`: ports only on 127.0.0.1, no default passwords, pinned
    images, `.env.example` has only placeholders.
  - Also applied the migration by hand to a real PostgreSQL 16 server on
    127.0.0.1 to confirm it isn't PGlite-specific.

## Design decisions worth explaining

- **Constraints in the database, not only in code.** The worker validates
  findings before writing them, but the API, a future migration script, or a
  bug can all write rows. CHECK constraints make impossible states
  (a SUCCEEDED scan with no grade, score 11 out of 10) unrepresentable. The
  app-side validation exists for readable errors; the DB is the backstop.
- **SQL's three-valued logic bit me, and the test caught it.** The first
  version of the alert-rule check was `kind = 'CERT_EXPIRY' AND days BETWEEN
  1 AND 365 OR kind <> 'CERT_EXPIRY' AND days IS NULL`. For a CERT_EXPIRY rule
  with `days = NULL`, that evaluates to `NULL OR FALSE` = `NULL`, and a CHECK
  only rejects `FALSE`, so the bad row was accepted. Adding `days IS NOT NULL`
  fixed it. Lesson: always test the NULL case of a CHECK.
- **Why a real Postgres in tests, without Docker.** Mocking Prisma would test
  nothing about the schema. PGlite is Postgres 17 compiled to WebAssembly,
  running in the test process; `pglite-socket` exposes it on 127.0.0.1 over
  the normal wire protocol, so the production code path (`pg` driver ->
  Prisma adapter -> SQL) is what's tested. CI needs no service containers.
  Compose uses Postgres 17 to match.
- **Drift detection without the migration engine.** If `schema.prisma` and
  `migration.sql` disagree (renamed column, missing enum value), the client
  test's queries fail, and the enum test compares `pg_enum` to the generated
  enums directly. This also covers environments where Prisma's schema-engine
  binary can't be downloaded.
- **Owner scoping is a schema property.** Every row can reach `sites.owner_id`
  by walking up foreign keys, and `(owner_id, url)` is unique per owner, not
  globally, so two users can monitor the same site without one learning that
  the other does. Step 14 builds authorization on this.
- **Cascade deletes.** Deleting an account must delete its data (privacy, and
  no orphaned rows that leak into aggregate queries). Doing it with FKs makes
  it atomic and impossible to forget in application code.
- **Prisma 7 specifics.** The connection URL lives in `prisma.config.ts`, not
  the schema, and queries go through a JS driver adapter (`@prisma/adapter-pg`)
  instead of a Rust query engine. The config only declares a datasource when
  `DATABASE_URL` is set, so `generate`/`validate` work in CI without a DB.
  The generated client is git-ignored and produced on install.
- **Safe-by-default compose.** Publishing `5432:5432` binds to 0.0.0.0, which
  exposes the database to the whole network, and Docker's iptables rules
  bypass host firewalls like ufw. Binding to `127.0.0.1:` and refusing to start
  without passwords removes the two most common self-hosting mistakes. The
  Redis password is read from the environment inside the container so it
  doesn't appear in `ps` output on the host.
- **Defensive data handling.** Finding details quote bytes from the scanned
  site; a NUL byte would make Postgres reject the insert, letting a hostile
  site make its own scan fail to save. `findingRows()` strips them. Status
  lookup uses a `Map`, so inputs like `"__proto__"` can't match an object key.
- **Dependency hygiene.** Pinned Prisma to the stable 7.10.1 (npm's `latest`
  tag currently points at an 8.0 release candidate), and overrode a
  vulnerable transitive `effect` instead of loosening the CI audit gate.

## How to try it

```bash
corepack enable && pnpm install                  # also generates the Prisma client
pnpm check                                       # lint + format + tsc + 878 tests
pnpm --filter @header-auditor/db test            # just today's 92 tests (no Docker needed)
cd cli-python && pytest -q                       # 119 tests

# Real local services
cp .env.example .env                             # set your own local passwords
docker compose up -d --wait
pnpm --filter @header-auditor/db migrate:deploy
```

```ts
import { createPrismaClient, findingRows, toDbGrade } from "@header-auditor/db";

const prisma = createPrismaClient(); // reads and validates DATABASE_URL
await prisma.scan.create({
  data: {
    siteId,
    status: "SUCCEEDED",
    requestedUrl: "https://example.test/",
    score: 92,
    grade: toDbGrade(report.grade),
    finishedAt: new Date(),
    findings: { createMany: { data: findingRows([["HEADERS", report.findings]]) } },
  },
});
```
