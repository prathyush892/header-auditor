# 2026-11-23: Sites CRUD (roadmap step 14)

## Plan

1. `apps/api/src/sites/url.ts`: turn whatever a user types into one canonical
   origin, and refuse IP literals, localhost and special-use names.
2. A `SiteStore` interface where every method takes the owner's id, with an
   in-memory implementation and a Prisma one. No migration needed: `sites`
   already exists from step 11.
3. Routes: list (cursor-paginated), create, read, update, delete. Every one
   goes through `requireAuth` and the CSRF hooks from step 13.
4. Config: a per-user site quota and a dev-only switch for private targets.
5. Tests that prove users can't see or change each other's sites, run
   against both the in-memory stores and real SQL (PGlite).

## Built

- **`sites/url.ts`**: `normalizeSiteUrl()` turns `Example.COM`,
  `https://example.com/`, `https://example.com.:443` into
  `https://example.com`. A missing scheme means https, unicode hosts are
  converted to punycode, the trailing root dot and default ports are dropped.
  Refused: non-http(s) schemes, credentials, any path/query/fragment, spaces
  and control characters, bad labels, IP literals (including `0x7f.0.0.1`
  and `2130706433`, which WHATWG `URL` turns into `127.0.0.1` first),
  single-label names and special-use suffixes (`localhost`, `.local`,
  `.internal`, `.home.arpa`, `.test`, `.onion`, ...). `normalizeHostname()`
  does the same for `firstPartyHosts` entries.
- **`sites/store.ts`**: `SiteStore` (`listSites`, `findSite`, `createSite`,
  `updateSite`, `deleteSite`). Each takes `ownerId` first. There is no
  method that loads a site by id alone. `MemorySiteStore` for tests,
  `SiteExistsError` and `SiteLimitError`.
- **`sites/prisma-store.ts`**: `createPrismaSiteStore(client)`, typed
  structurally like the auth store. `createSite` runs in a transaction that
  first takes `SELECT ... FOR UPDATE` on the owner's `users` row, then checks
  for a duplicate URL, then checks the quota, then inserts. Updates use one
  `UPDATE ... WHERE id AND owner_id` (Prisma `update` with
  `{ id, ownerId }`, P2025 → null). Deletes use `deleteMany` on the same pair.
- **`sites/cursor.ts`**: opaque cursors, base64url of `<createdAt ms>.<id>`.
  Strictly decoded: canonical base64url only, lower-case UUID, at most 15
  digits for the timestamp.
- **`sites/routes.ts`** (enabled with `buildApp({ auth, sites })`):
  - `GET /sites?limit=1..100&cursor=` → `{ items, nextCursor }`, newest
    first.
  - `POST /sites` `{ name, url, schedule?, firstPartyHosts? }` → `201` with
    `Location: /sites/:id`. `409 SITE_EXISTS` for the same origin spelled any
    way, `409 SITE_LIMIT_REACHED` at the quota.
  - `GET /sites/:id`, `PATCH /sites/:id` (`name`, `schedule`,
    `firstPartyHosts`; the URL can't be changed), `DELETE /sites/:id` → 204.
  - Someone else's site, a missing site and a malformed id all return the
    same `404 SITE_NOT_FOUND`.
  - `schedule` other than `none` returns `409 SITE_NOT_VERIFIED` until the
    site is verified (verification itself is step 17).
  - Bodies are strict: `ownerId`, `verifiedAt`, `verificationToken` or `url`
    in a PATCH are rejected (400), not silently ignored.
  - The response includes the 64-hex-character `verificationToken` the owner
    will publish in DNS. It never includes `ownerId`.
- **Config**: `SITES_MAX_PER_USER` (default 50) and
  `SITES_ALLOW_PRIVATE_TARGETS` (default false, refused in production). Both
  are documented in `.env.example`.
- `buildApp` throws if `sites` is passed without `auth`. `start()` logs a
  warning when no site store is configured, like it does for auth.
- **Tests**: api 267 → 459. URL rules 73, cursors 13, the store contract
  26 (11 behaviours × memory and PGlite, plus 4 Postgres-specific), routes
  75 (an authorization suite of 9 cases run on both backends, plus CRUD,
  validation, CSRF, pagination, quota and schedule gate), config +5. db 99,
  core 786 and pytest 119 are unchanged. ESLint (strictTypeChecked +
  security), Prettier, `tsc`, bandit and the secrets grep are clean. `pnpm
  audit` still shows only the known dev-only moderate `minimatch` advisory.
- Sanity check on the tests: I removed `ownerId` from the Prisma `findSite`
  query on purpose. `tsc` refused to compile it (the structural client type
  requires `ownerId` in that `where`), and with the type check bypassed, 3
  authorization tests failed. Then I restored it.

## Design decisions worth explaining

- **IDOR is the bug this step exists to prevent.** An Insecure Direct Object
  Reference is `GET /sites/123` returning site 123 to whoever asks, because
  the code checked "is someone logged in" but not "is it theirs". It's the
  most common API flaw (OWASP API Security Top 10 #1, "Broken Object Level
  Authorization"). The defence here is structural, not "remember to add a
  check": the store has no unscoped lookup, so every query is
  `WHERE id = $1 AND owner_id = $2`. The Prisma client type even requires
  `ownerId` in those `where` clauses, so leaving it out doesn't compile.
- **404, not 403, for someone else's site.** A 403 says "this exists, but
  not for you", which lets an attacker enumerate ids. The tests compare
  Bob's response for Alice's site with his response for a random UUID: same
  status, code, message and fields. A malformed id also returns 404 rather
  than 400, for the same reason.
- **Authorization proven on real SQL.** The same 9-case suite (Alice can,
  Bob can't: list, GET, PATCH, DELETE, cursor reuse, same URL for both)
  runs against the in-memory stores and against PGlite through Prisma. A
  test double can't catch a wrong `WHERE` clause.
- **Single-statement update and delete.** `UPDATE sites SET ... WHERE id = $1
  AND owner_id = $2` does the check and the write in one statement. The
  alternative, "load the site, check the owner in JS, then update by id",
  leaves a window between the check and the write (TOCTOU, time-of-check to
  time-of-use) and a second query where the owner filter can be forgotten.
- **Quota without a race.** "Count, then insert" fails under concurrency:
  two requests both count 49 and both insert. Locking the owner's `users`
  row (`FOR UPDATE`) makes one user's creates queue up for the duration of
  the transaction, while other users aren't blocked. The unique index
  `(owner_id, url)` is the final backstop for duplicates, mapped to
  `SiteExistsError`. Honest caveat: PGlite runs one connection, so the
  concurrency test proves the logic, not the lock. Real Postgres in CI is
  step 25's job.
- **Canonical origins.** The scanner, the unique index and DNS verification
  all work on origins. If `example.com` and `https://EXAMPLE.com:443/` were
  stored as different strings, the duplicate check would miss them, scans
  would run twice, and verification could apply to one row but not the
  other. Rejecting paths (instead of silently dropping them) means the user
  never thinks `/admin` is being scanned when it isn't.
- **IP and localhost refusal is a filter, not the SSRF control.** Refusing
  `http://169.254.169.254` (the cloud metadata endpoint) at creation gives a
  clear error early. But `evil.example.com` can resolve to `10.0.0.1`, or
  switch to it after a check (DNS rebinding). The real control is the
  connect-time address check in `packages/core` `scanUrl` (step 5), which
  the worker uses in step 15. Defence in depth: two layers, and the second
  doesn't trust the first. `SITES_ALLOW_PRIVATE_TARGETS` exists so the e2e
  test (step 26) can scan a mock server on 127.0.0.1, and the config refuses
  it in production.
- **The URL is immutable.** Changing it would make an existing verification
  and the scan history describe a different site. To change the URL, delete
  the site and add a new one, which gives a new token and a clean history.
- **Schedule gated on verification now.** Scheduled scans of an unverified
  domain would let anyone use this service to scan a site they don't own on
  a timer. Rejecting `daily`/`weekly` until `verifiedAt` is set means step
  17 only has to set that field: no path exists today that could create the
  problem.
- **Keyset pagination with an opaque cursor.** `OFFSET 1000` makes Postgres
  read and throw away 1000 rows, and rows shift between pages when sites
  are added or deleted. A keyset query `WHERE (created_at, id) < (cursor)
  ORDER BY created_at DESC, id DESC` uses the `(owner_id, created_at)` index
  and never skips or repeats a row. The `id` tie-breaker matters because two
  sites can share a millisecond. The test sets equal timestamps on purpose.
  The cursor isn't signed because it doesn't need to be: the query is
  always owner-scoped, so a forged cursor only moves you within your own
  list. The test hands Bob Alice's cursor to prove it. Fetching `limit + 1`
  rows tells us whether a next page exists without a `COUNT(*)`.
- **Strict bodies (mass assignment).** `z.strictObject` rejects unknown
  keys. So `{"ownerId": "<someone else>"}` or `{"verifiedAt": "..."}` is a
  400, not a field that some later refactor might start copying into the
  database.
- **Verification token: 32 random bytes, hex.** 256 bits can't be guessed,
  hex is safe in a DNS TXT record, and 64 characters fits the existing
  `VARCHAR(64)` and its `>= 32` CHECK constraint. Each site gets its own
  token, even for the same URL under two owners, so one user's DNS record
  can't verify another user's row.

## How to try it

```bash
corepack enable && pnpm install
pnpm --filter @header-auditor/api test     # 459 tests (PGlite on 127.0.0.1 for the Prisma stores)
```

In code:

```ts
import { buildApp, loadConfig, MemoryAuthStore, MemorySiteStore } from "@header-auditor/api";

const app = await buildApp({
  config: loadConfig(),
  auth: { store: new MemoryAuthStore() },
  sites: { store: new MemorySiteStore() }, // or createPrismaSiteStore(prismaClient)
});
```

Against a running app (`AUTH_COOKIE_SECURE=false`, after registering as in
the 2026-11-22 note):

```bash
H='-H content-type:application/json -H origin:http://localhost:3000 -H x-csrf-token:<csrfToken>'
curl -s -b jar $H -d '{"name":"Blog","url":"Blog.Example.com"}' http://127.0.0.1:3001/sites
curl -s -b jar 'http://127.0.0.1:3001/sites?limit=10'
curl -s -b jar -X PATCH $H -d '{"schedule":"daily"}' http://127.0.0.1:3001/sites/<id>   # 409 SITE_NOT_VERIFIED
curl -s -b jar -X DELETE $H http://127.0.0.1:3001/sites/<id>                           # 204
```

`apps/worker` runs `packages/core` and stores the results.

Known gaps:

- **Postgres at startup** moves to step 15. The worker and the API both need
  a runnable `@header-auditor/db`, which currently exports TypeScript
  source. Building it once for both consumers is cleaner than a one-off in
  the API. Until then `start()` takes injected stores.
- A per-user rate limit on `POST /sites` (the quota caps the total, not the
  churn of create/delete).
- Prove the `FOR UPDATE` serialisation against a multi-connection Postgres
  (CI service container) once CI runs Postgres.
- Step 17 verification: TXT record `header-auditor-verification=<token>`,
  set `verifiedAt`, and decide whether verification expires and is
  re-checked before each scheduled scan.
