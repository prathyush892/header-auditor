# 2026-11-15: TLS check (roadmap step 6)

## Plan
1. Split the work in two: a **probe** that opens TLS handshakes and records
   what it saw as plain data (`TlsSnapshot`), and **pure checks** that grade a
   snapshot. Same split as headers (`scanUrl` → `runAll`).
2. Reuse the SSRF guard from step 5 for every handshake (IP literals up front,
   hostnames inside the socket's own DNS lookup).
3. Probe TLS 1.0 and 1.1 separately, offering only that one version, to see if
   the server still *accepts* them, not just what it prefers.
4. Test against local TLS servers on 127.0.0.1 with certificates minted at test
   time by a throwaway CA, so no private key is ever committed.
5. Give `scanUrl()` an https test path: a `ca` option and a `TLS_ERROR` code.

## Built
- `tls/types.ts`: `TlsSnapshot`, `CertificateInfo`, `CipherInfo`, and the
  `accepted | rejected | untested` result for each legacy version.
- `tls/analyze.ts` (pure, no sockets): seven checks, each returning a `Finding`:
  - **TLS protocol** (15 pts): 1.2/1.3 pass (1.2 suggests enabling 1.3); anything older fails.
  - **Legacy TLS versions** (15): fails if TLS 1.0 or 1.1 is accepted; `info` if untestable.
  - **Cipher suite** (15): `classifyCipher()` → `insecure` (NULL/export/RC4/DES/3DES/anon/MD5, 0 pts),
    `no-forward-secrecy` (static RSA, 5), `cbc` (10), `strong` (AEAD + (EC)DHE, or any TLS 1.3 suite, 15).
  - **Certificate validity** (20): not-yet-valid / expired fail with 0; ≤7 days left fails with 5;
    ≤30 days warns with 12. Thresholds and the clock (`now`) are options.
  - **Certificate hostname** (20): uses Node's `tls.checkServerIdentity` (RFC 6125).
  - **Certificate trust** (15): chain verified against the trust store; self-signed and
    untrusted-issuer get different messages; an expired-only error gets partial credit
    so the date problem isn't counted twice.
  - **Certificate key** (10): RSA < 2048 or EC < 256 bits fails.
  - `buildTlsReport()` scores them with the existing `scoreFindings` and adds a **grade cap**:
    a zero-score failure on protocol, validity, hostname or trust forces grade F
    (`gradeCappedBy` lists which).
- `tls/probe.ts`: `probeTls(url, options)` → `TlsReport`. One main handshake
  (offers TLS 1.0–1.3, records the negotiated protocol, cipher, leaf cert and
  verification result), then TLS 1.0 and 1.1 probes in parallel. Options:
  `timeoutMs`, `probeLegacy`, `allowPrivate`, `allowAddresses`, `resolver`, `ca`,
  `signal`, `now`, `expiryWarnDays`, `expiryCriticalDays`, all validated before
  any socket opens. `certificateInfo()` flattens Node's `PeerCertificate`.
- `scanUrl()`: new `ca` option (trust a private CA, used by the tests), and
  certificate/handshake failures now map to the new `ScanError` code `TLS_ERROR`
  instead of the generic `NETWORK`. Certificate errors are still never ignored there.
- `test/helpers/pki.ts`: `TestPki` creates a CA and leaf certs (EC P-256, RSA 2048, RSA 1024,
  self-signed or CA-signed, any validity) with the `openssl` CLI in a temp dir, deleted after the run.
- Tests: 387 Vitest tests (was 290): 64 in `tls-analyze.test.ts` (pure fixtures)
  and 33 in `tls-probe.test.ts` (local TLS/HTTPS servers). pytest unchanged at 119.
  ESLint (security plugin, zero warnings), Prettier, `tsc`, bandit, the secrets grep
  and `pnpm audit --audit-level=high` are all clean.

## Design decisions worth explaining
- **Observe, don't enforce, but only because nothing is sent.** A browser
  aborts on a bad certificate. A scanner can't, or it could never *report* the bad
  certificate. So the probe uses `rejectUnauthorized: false` and records
  `authorized`/`authorizationError` instead. That's only safe because the probe
  never writes application data (a test asserts the server received 0 bytes after
  the handshake). `scanUrl()`, which does send an HTTP request, keeps full
  verification and fails with `TLS_ERROR`. Keeping those two apart is the point.
- **"Accepts" is not the same as "prefers".** A server that negotiates TLS 1.3 with a modern
  client may still accept TLS 1.0 from an old one, and a downgrade attacker
  would choose that. The only way to know is to offer *only* TLS 1.0 (min = max = TLSv1)
  and see whether the handshake finishes. Same for 1.1. If our own OpenSSL can't
  offer a version, the result is `untested`, not `rejected`, so we never claim a
  pass we didn't verify.
- **Probe connections run at OpenSSL security level 0.** Modern OpenSSL refuses
  TLS 1.0 and small keys by default, which would make the scanner blind to the
  exact servers it should flag. `DEFAULT@SECLEVEL=0` is set only for these
  handshake-only connections. It's never used to fetch content.
- **Snapshot, then grade (pure functions).** All the grading logic is
  deterministic and tested with fixtures: an expired cert is a `validTo` in the
  past, not a server we have to wait for. The clock is injectable (`now`), and a
  stored snapshot can be re-graded later when the rules change, without
  reconnecting.
- **Grade caps.** Weighted points answer "how good is this config overall",
  but some failures are binary: browsers show a hard error for a self-signed or
  wrong-host certificate. Averaged in with a good cipher, a self-signed cert still
  scored 55 ("D"), which is misleading. Like SSL Labs, a zero-score failure on a
  blocking check forces an F. The numeric score is kept so two failing scans can
  still be compared.
- **Don't hand-roll hostname matching.** Wildcard rules are a classic source of
  bugs: `*.app.test` must match `www.app.test` but not `a.b.app.test` or
  `evil-app.test`, the CN is ignored once SANs are present, and IPs only match IP
  SANs. `tls.checkServerIdentity` already implements RFC 6125, and using it means
  the scanner agrees with real Node clients. Tests pin those edge cases.
- **SNI only for names.** The probe sends the hostname as SNI so virtual-hosted
  servers return the right certificate, but never an IP (RFC 6066 forbids it).
- **No committed keys.** The test CA and leaf keys are generated with `openssl`
  at test time in a `mkdtemp` directory and deleted afterwards. A repo that
  contains a PEM private-key block trips secret scanners and teaches bad
  habits, even when the key is a test key.
- **Same SSRF policy as HTTP.** A TLS handshake is still a connection from our
  network to a user-chosen address. Blocked targets fail before connecting
  (tests check the server's connection counter didn't move).

## How to try it
```bash
corepack enable && pnpm install
pnpm check                                          # lint + format + tsc + 387 vitest tests
pnpm --filter @header-auditor/core test tls         # TLS unit + integration tests
cd cli-python && pytest -q                          # 119 tests
```

```ts
import { probeTls } from "@header-auditor/core";

// Against your own local https dev server (private targets need explicit opt-in):
const tls = await probeTls("https://127.0.0.1:8443/", { allowPrivate: true });
console.log(tls.grade, tls.score, tls.gradeCappedBy);
for (const f of tls.findings) console.log(f.status, f.check, f.detail);
```

## Next
Roadmap step 7: HTTP→HTTPS redirect check and mixed-content detection in the
returned HTML. That needs the bounded body read that `scanUrl` doesn't do yet,
and it's the natural place to flag https→http downgrades in a redirect chain.

Known gaps to pick up later:
- Weak ciphers are judged from the *negotiated* suite only. Listing every suite
  the server accepts (one handshake per suite) would be more thorough; our
  OpenSSL build doesn't even include RC4/DES, so those can't be offered anyway.
- No signature-algorithm check (SHA-1 certs), OCSP/stapling, or full chain
  inspection yet. Node's `PeerCertificate` doesn't expose the signature
  algorithm directly; `crypto.X509Certificate` parsing could add it.
- `probeTls` isn't wired into a combined "full scan" yet. The worker (step 15)
  will run `scanUrl` + `probeTls` together and store both.
